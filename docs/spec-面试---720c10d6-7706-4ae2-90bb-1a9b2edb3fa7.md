# AI Coding Agent 岗位定制面试题库

> 基于两个独立项目整理：**AI-AI-Coding** 与 **IOC（AIOperationsCenter）**。  
> 使用原则：只讲代码、文档和验收能够证明的内容；把“已实现”“设计方案”“待验证收益”明确分开。

## 一、两个项目的定位

| 项目           | 主要证明能力                                                                         | 不应夸大的内容                                                                   |
| -------------- | ------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------- |
| AI-AI-Coding   | SDD、Prompt/Rules/Skills、研发流水线、Harness、代码资产复用、自动验证、Vue/TS 工程化 | 尚未配置 CI；尚无真实团队长期试点；“天级到小时级”“效率 +30%”只是目标             |
| IOC            | LangGraph Agent、Tool Calling、RAG、Prompt 治理、Trace/LangSmith、多步分析、失败降级 | LangSmith 主要是代码和 Fake Client 验收；不是 Codebase RAG；没有游戏项目生产经验 |
| cascade-filter | 从模糊需求到 PRD-SPEC、HLD、LLD 和真实组件代码的 SDD 案例                            | 尚不能说完整上线；专项测试、TASKS、Review、上线验收材料还不完整                  |

## 二、推荐核心叙事

> 我有两个互补项目。  
> AI-AI-Coding 解决的是“AI 如何稳定地产出符合团队规范、能进入工程交付的代码”。我把 Prompt、Cursor Rules、可执行 ai-kit、Codegen Skill、检索器、安装器和验证命令串成开发期工作流，并通过 cascade-filter 实践了从模糊需求到 PRD-SPEC、HLD、LLD 和组件实现的 SDD 链路。  
> IOC 解决的是“Agent 如何在真实业务链路中可靠运行”。项目使用 LangGraph 编排多步分析，通过 Tool Center 调用 KPI、告警、隐患和工单工具，并接入报告追问、RAG、Prompt 版本治理和 LangSmith Trace。  
> 因此，我既做过 AI Coding 的生成侧工程，也做过 Agent 的运行侧工程。下一步希望把两边经验组合成面向游戏 A/B 实验的产品级 AI Coding Pipeline。当前本地工程闭环已有证据，真实效率收益和游戏场景效果需要通过试点验证。

不要再背：

> 效率 +30%、冗余代码 -40%、质量 +50%。

除非能拿出基线、样本、统计口径和原始记录。

# 第二组：AI-AI-Coding 项目深挖

## 6. AI-AI-Coding 不就是一个 Prompt 仓库吗？★★★★★

它不只有 Markdown Prompt，还包含：

- 50 条 Cursor Rules；
- 17 个场景 Prompt；
- 15 个 Vue/TypeScript ai-kit 实现文件；
- Prompt—Rules—References 自动关联；
- Codegen Skill；
- 业务项目安装器；
- 类型检查、契约检查、Node/Vitest 测试和安全审计；
- Prompt Lab。

真正形成的是：

```text
需求
→ 检索任务模板
→ 加载规则和可信实现
→ 检查目标项目事实
→ 在业务仓库生成
→ 运行验证
```

## 7. Rules、Prompt、ai-kit、Skill 分别解决什么问题？★★★★★

- **Rules**：长期约束，例如禁止 `any`、必须复用已有请求层。
- **Prompt**：本次任务的目标、字段、交互和验收条件。
- **ai-kit**：真实可执行参考，回答“具体怎么写”。
- **Skill**：多步骤工作流，规定什么时候触发、按什么顺序执行、交付什么。
- **目标项目代码**：最终事实来源，优先级高于 AICoding 的通用示例。

一句话：

> Rules 管约束，Prompt 管任务，ai-kit 管事实，Skill 管过程。

## 8. 为什么不写一个超长 System Prompt？

- 上下文噪声增加；
- 无关规则可能冲突；
- Token 成本增加；
- 修改难以评审和版本化；
- AI 难以判断哪些规则适用于当前场景。

当前方案是渐进式披露，只加载最相关 Prompt、规则和引用文件。

## 9. Prompt 如何检索？为什么没有使用向量数据库？

> 当前只有 17 个任务 Prompt，使用关键词、别名、标题、路径和正文评分，结果可解释、可离线测试。引入向量检索会增加 Embedding、索引、服务和版本治理成本。只有当 Prompt 数量、同义表达和跨领域检索明显超出规则评分能力时，我才会升级为关键词召回加向量召回的混合检索。

注意：这不是 Codebase RAG，不能说已经实现三层代码索引。

## 10. AI 如何避免虚构接口、字段和依赖？★★★★★

1. 先读目标项目 `package.json`、类型、API 层和相似页面；
2. 优先复用目标项目已有组件；
3. Prompt 示例只作为结构参考；
4. 缺少关键业务事实时明确提出问题；
5. 生成后运行目标项目的 type-check、test、lint、build；
6. 报告未验证项，不能用 Mock 通过代替真实接入。

## 11. 为什么 ai-kit 默认不是业务项目的运行时依赖？

- 不同项目的 Vue、Element Plus、ECharts 和主题版本不同；
- 业务项目可能已有自己的 BaseComponent；
- 强制直接依赖会增加升级耦合；
- 默认作为开发期参考，目标项目资产优先；
- 只有明确安装或复制对应资产后才能直接 import。

## 12. 如何防止规则与代码实现发生漂移？

**项目证据：**

- 校验 `.mdc` frontmatter；
- 校验规则引用路径存在；
- 检查 ai-kit 源码中的 `any`；
- Vue 严格类型检查；
- Node 和 Vitest 测试；
- Prompt 静态目录与源文件一致性检查；
- npm 打包预检验证必要资产确实进入发布包。

**进一步改进：** 在 CI 中执行完整检查，建立规则测试集，为每条规则增加 owner、版本和失败案例来源。

## 13. `useRequest` 如何处理请求竞态？

- 每次请求递增序号；
- 只有最新请求可以写入 `data/error/loading`；
- 旧请求即使后返回，也不能覆盖新结果；
- 当前 cancel 主要是结果失效；
- 真正网络中止应在 Service 层传递 `AbortSignal`。

**追问：为什么不能只用防抖？**  
防抖只能减少请求，不能保证所有已发请求的返回顺序。

## 14. `useDialog` 为什么返回 Promise？

- 调用方能像等待确认操作一样接收结果；
- 避免多组件间散落回调；
- 重复打开时先用 `false` 结束上一次 Promise，避免悬空；
- loading 状态锁定关闭入口；
- 异步关闭拦截异常通过事件上报。

## 15. `useChart` 最难处理的工程问题是什么？

- DOM 挂载前 option/loading 已经到达；
- 主题切换需要重建实例；
- ResizeObserver 和窗口监听需要释放；
- 高频更新需要合并；
- 深度监听大型 option 成本高；
- 卸载时必须清理实例、监听器和定时器。

## 16. 你如何证明仓库自身是可执行的？

可以引用的历史验收证据：

- 50 条规则契约检查通过；
- 15 个 Vue/TS 文件严格类型检查通过；
- 9 项 Node 测试；
- 10 项 Vitest；
- ECharts 6.1.0；
- 当次安全审计 0 漏洞；
- npm 打包预检包含 107 个文件。

边界：这些证明仓库自身契约可执行，不等于所有业务项目都能零修改接入。

# 第三组：SDD 与 cascade-filter 案例

## 17. 你怎么理解 SDD？★★★★★

> SDD 不是先写很多文档，而是先把需求转成机器和人都能检查的契约，再让设计、任务、代码、测试和验收都引用同一份契约。它的价值是减少 AI 在隐含需求上的猜测，并把错误尽量前移到低成本阶段发现。

## 18. 你在项目中如何落地 SDD？★★★★★

```text
模糊需求
→ PRD-SPEC：明确目标、边界和验收
→ HLD：确定模块、数据流、接口与 ADR
→ LLD：写死组件 API、类型和测试要点
→ 代码与验证
→ 按 Spec 验收并回流失败案例
```

**当前真实边界：**

- cascade-filter 已有 PRD-SPEC、HLD、LLD 和组件实现；
- LLD 仍标记“评审中”；
- 专属 TASKS、测试、Code Review 和上线验收材料还需补齐；
- 因此应称为“SDD 实操案例”，不要说已经完整生产交付。

## 19. Spec 至少应该包含哪六类信息？★★★★★

1. 背景、用户与目标；
2. 功能行为和优先级；
3. 输入、输出和接口契约；
4. 状态、异常和边界条件；
5. 非功能要求与约束；
6. 可验证的验收标准和观测指标。

## 20. cascade-filter 最初需求是什么？你做了哪些澄清？

从“一句话三级筛选框”澄清出：

- 是通用组件，不绑定省市区或组织；
- 数据逐级懒加载；
- UI 使用 Cascader；
- “不限”动态配置；
- 支持已有值回显；
- 上级变化必须清空下级；
- 失败要显示错误并允许重试；
- 只选到二级也可作为有效筛选范围。

## 21. cascade-filter 的关键架构决策是什么？

四个 ADR：

1. Cascader，而不是三个独立下拉；
2. 懒加载，而不是全量加载；
3. 注入 `fetchOptions`，而不是组件写死 URL；
4. `allowEmpty` 配置化，而不是写死业务行为。

**追问：为什么使用函数注入？**  
隔离鉴权、URL 和数据格式差异，使组件只依赖稳定领域契约。

## 22. cascade-filter 如何处理回显？

- 设置 `hydrating`，回显过程中禁止操作；
- 一级到三级顺序加载；
- 每级校验目标 ID 是否存在；
- 某级值失效时截断到上一级；
- 回显同步 `modelValue`，但不触发用户主动的 `change`；
- 懒加载与预热并发时通过 in-flight Promise 去重。

## 23. cascade-filter 当前设计里有什么潜在问题？★★★★★

- `CascadeLevel` 写死为 `1 | 2 | 3`，但 Props 又声称支持 2/3/4 级，类型与能力存在冲突；
- 缓存主要以 level 为键，若同一级切换不同 parent，可能返回错误父节点的数据；更合理的缓存键应为 `level + parentId`；
- LLD 写了组件测试，但当前目录未看到对应专项测试；
- 加载失败主要用消息提示，是否真正提供面板内“重试按钮”需要继续实现；
- PRD 要求清空下级，但当前组件依赖 Cascader 内部值变化，需验证缓存清理是否完整触发。

## 24. 你是否实现了 Spec DSL？

> 当前实现的是结构化 Markdown 模板和文档约定，还不是有解析器、Schema 校验和编译能力的正式 DSL。我会把它称为 Spec Schema 或模板体系。下一步可以将核心字段抽成 YAML/JSON Schema，进行静态校验，再生成任务、测试骨架和发布元数据。

不要说：“我已经设计并上线了 Spec DSL。”

# 第四组：Harness 与端到端流水线

## 25. 什么是 Harness Engineering？★★★★★

> Harness 是包围模型生成过程的一组确定性工程设施，包括上下文准备、工具权限、执行沙箱、编译测试、质量评分、失败恢复和发布门禁。模型负责提出候选实现，Harness 负责证明它是否可以进入下一阶段。

## 26. 你会如何设计六层 AI Coding Harness？★★★★★

```text
L1 Spec Harness
   校验目标、接口、边界和验收条件是否完整

L2 Context Harness
   检索相关规则、代码、依赖和相似实现，检查引用有效性

L3 Generation Harness
   限制文件范围、工具权限、依赖和变更预算

L4 Static Harness
   格式、lint、类型检查、依赖与安全扫描

L5 Runtime Harness
   单测、组件测试、集成测试、构建、游戏运行测试

L6 Delivery Harness
   Diff Review、风险评分、人工审批、灰度、回滚和线上观测
```

与项目对应：

- AI-AI-Coding 已较好覆盖 L1、L2、L4 和部分 L5；
- L3 有 Skill/Rules 的流程约束，但还可加强沙箱和权限；
- L6 的 CI、真实试点、灰度和线上指标尚未闭环。

## 27. 请设计一条“Spec 进、部署出”的流水线。★★★★★

```text
需求输入
→ Spec 完整性检查
→ HLD/LLD 与风险分级
→ 任务依赖图
→ 建隔离分支或工作区
→ Codebase Context 检索
→ AI 生成代码
→ 静态检查
→ 单元/集成/构建/游戏测试
→ 自动 Review 与风险评分
→ 人工批准
→ 灰度部署
→ 指标观察
→ 自动停止或回滚
```

**关键设计点：**

- 幂等：每个任务有唯一 Spec ID；
- 可恢复：阶段产物持久化，可从失败节点重试；
- 隔离：每个变体独立分支和构建产物；
- 可追踪：Spec、Prompt、模型、代码提交和构建关联；
- 门禁：高风险变更不允许自动部署；
- 回滚：保留上一稳定构建和配置。

## 28. 如何把“天级变小时级”变成可验证目标？

| 阶段                | 需要采集的指标         |
| ------------------- | ---------------------- |
| 需求到 Spec 定版    | 澄清轮数、等待时长     |
| Spec 到首个候选代码 | 模型执行时长           |
| 首次生成到检查通过  | 人工修改时长、重试次数 |
| 检查通过到可 Review | 构建与测试时长         |
| Review 到实验包     | 人工等待和部署时长     |

核心指标包括 Lead Time、首次通过率、人工干预率、重试次数、阶段失败分布以及 P50/P90 交付时长。

## 29. 如何提高首次通过率？

1. 分析失败发生在哪一层；
2. 补齐 Spec 的输入输出和边界；
3. 改进检索，让模型获得正确相似代码；
4. 固化高频失败为规则；
5. 将失败案例加入回归数据集；
6. 减少一次任务的变更范围；
7. 对不同任务选择不同模型或 Prompt；
8. 不能靠减少测试“提高通过率”。

## 30. 如何降低人工干预率？

- 把重复澄清项写进 Spec 模板；
- 把重复 Review 问题变成静态规则；
- 让错误输出结构化并自动分类；
- 允许低风险失败自动修复并有限重试；
- 超过重试预算或触及高风险目录时升级人工；
- 关注“有效干预”，不能为了指标取消必要审批。

# 第五组：IOC Agent 项目深挖

## 31. IOC 的 Agent 主链路是什么？★★★★★

```text
页面上下文
→ LangGraph 运营分析
→ Tool Center 查询 KPI/告警/隐患/工单
→ 规则识别与 LLM 原因分析
→ 建议和报告汇总
→ 报告追问
→ 需要依据时调用 RAG
→ Trace、事件和结果持久化
```

技术栈：前端 Vue 3/TypeScript；后端 FastAPI/Python；REST + SSE；MySQL；DeepSeek/OpenAI-compatible 模型。

## 32. 为什么使用 LangGraph，而不是普通链式调用？

- 节点和状态边界清晰；
- 支持条件分支、失败降级和恢复；
- Tool/RAG/LLM 可以分别观测；
- 中间证据可以进入 State；
- 便于扩展报告追问、多 Agent 或人工确认节点。

加分点：如果流程始终只有一次 Prompt 和一次模型调用，不会为了框架而使用 LangGraph。

## 33. Tool Center 解决了什么问题？★★★★★

- 统一工具注册与发现；
- 统一输入输出契约；
- 统一错误语义和 `retryable`；
- 统一 Trace、耗时和 Evidence；
- Graph、API 和其他 Agent 共用同一工具层；
- Query、Analysis、Action 分层；
- Action 类型工具支持人工确认。

## 34. 工具调用如何避免越权或误操作？

- 查询、分析、动作工具分级；
- 工具白名单；
- 参数 Schema；
- 用户和页面上下文透传；
- 动作工具默认只生成草稿；
- `requires_human_confirmation`；
- 超时、重试和审计；
- 敏感输入脱敏；
- 生产环境再叠加 RBAC 和网关授权。

## 35. IOC 的 RAG 与 Codebase RAG 有什么区别？★★★★★

- IOC RAG：检索制度、标准和案例，为业务回答提供依据。
- Codebase RAG：检索代码符号、依赖、调用链和历史变更，为代码生成提供上下文。
- AI-AI-Coding 当前是关键词规则检索，不是完整 Codebase RAG。

## 36. 如果设计 Codebase RAG，你会如何做三层索引？

1. **文件层**：目录、语言、模块、README 和配置；
2. **符号层**：类、函数、组件、Hook、类型、API 与 import 图；
3. **语义/历史层**：代码块 Embedding、提交记录、Review 结论和失败案例。

```text
关键词/BM25 召回
+ 符号与依赖图扩展
+ 向量召回
→ 权限过滤
→ 重排
→ 按 Token 预算组装上下文
```

这是基于现有经验给出的演进设计，不应包装成已实现。

## 37. IOC 如何做可观测性？★★★★★

- 本地 `trace_id`：请求、日志、工具和数据库审计；
- LangGraph 节点事件：节点开始、完成、失败和耗时；
- LangSmith Trace：Graph、Node、LLM、Tool、RAG 的父子执行树。

Prompt 治理还记录：`prompt_key`、`prompt_version`、`prompt_commit_hash`、`environment`。

## 38. LangSmith 在项目中真实做到了什么？

> 代码层已完成 Graph/Node/LLM/Tool/RAG 的 Trace 接入、脱敏、采样和本地 traceId 关联；Prompt 发布前的 private Commit 同步、失败保护和 Commit 复用使用 Fake Client 做了自动化验收。本轮没有用真实账号上传业务 Prompt 和 Trace，因此远程端到端仍需隔离环境验证。

## 39. Prompt 管理中心为什么不是普通 CRUD？

- System、Business、Runtime Context、User Question 分层；
- 不可变版本；
- 草稿、审核、发布和回滚状态；
- production 读取 active release，不读取最新草稿；
- 测试、评估、实验和失败案例；
- Graph 节点记录版本事实；
- 发布前 LangSmith Commit 同步；
- 管理中心异常时回退本地 Prompt。

## 40. IOC 中最值得讲的排障案例是什么？

建议讲“后端成功但前端失败”：

- 创建版本接口返回 200；
- 随后的预览接口返回 422；
- 前后端对字段契约理解不一致；
- 项目已有 PreviewRequest，但路由复用了 RenderRequest；
- 统一为 `version_id` 并补 API 回归测试。

这能说明你会按完整请求链排查，而不是看到数据库写入成功就停止。

# 第六组：游戏 A/B 实验场景题

## 41. 一个玩法如何一天生成 5–10 个变体？★★★★★

```text
基础玩法 Spec
+ 可变参数 Schema
+ 约束条件
+ 变体矩阵
→ 生成 5–10 份 Variant Spec
→ 每份创建隔离分支
→ AI 修改受限文件
→ Harness 自动验证
→ 生成独立构建
→ 接入实验配置
```

可参数化内容：方块生成概率、难度曲线、奖励频率、UI 反馈强度、引导节奏和关卡目标。

关键约束：配置优先；保证变体互斥；每个变体有唯一 ID；实验指标和停止规则在生成前定义。

## 42. 如何避免十个变体变成十条维护分支？

- 优先参数化和配置化；
- 使用 Feature Flag/Remote Config；
- 稳定逻辑共用；
- 只有机制差异才生成代码；
- 变体过期后及时归档；
- 获胜变体合并为主路径，其他变体删除；
- 配置 Schema 和代码版本绑定。

## 43. 变体生成后如何自动验证？

1. Spec/配置 Schema 校验；
2. C#/TS 编译；
3. 单元测试；
4. Unity EditMode/PlayMode 测试；
5. 资源和场景引用检查；
6. 固定随机种子的模拟运行；
7. 性能、内存和包体积阈值；
8. 关键页面截图或视频差异；
9. 埋点完整性检查；
10. 人工试玩门禁。

## 44. 如何判断 A/B 实验结果可信？

- 实验前明确主指标和护栏指标；
- 随机分流且用户稳定分桶；
- 样本量估算；
- 避免中途反复偷看并提前下结论；
- 检查新用户、国家、设备等分层；
- 同时看留存、时长、付费、崩溃和性能；
- 多变体时控制多重比较；
- 结果显著不代表业务价值一定足够大。

## 45. 如果没有 Unity 经验，如何做 Unity Prompt 优化？

> 我不会把 Vue 的 Prompt 直接平移到 Unity。我会先提取 Unity 项目的真实约束：程序集、场景、Prefab、MonoBehaviour 生命周期、序列化字段、资源加载方式和测试命令。然后建立 Unity 专属 Rules 与 Few-shot，加入禁止在 Update 中分配内存、资源释放、主线程限制等约束，再用编译、EditMode、PlayMode 和真机性能数据评估。

# 第七组：压力追问与边界防守

## 46. 你说端到端流水线，为什么项目里还没有 CI？

> 当前跑通的是本地可执行流水线和文档门控，CI 是明确缺口，所以我不会称它为生产级无人交付平台。下一步会先把 `npm run check`、安全审计、打包预检和最小业务示例接入 CI，再逐步增加隔离分支、构建产物和部署门禁。

## 47. cascade-filter 为什么还不能证明“Spec 进、部署出”？

> 它已经证明了从需求澄清到设计和实现的链路，但部署侧证据不足：专项测试、Code Review、上线 Checklist 和真实业务接入尚未完整。因此它是 SDD 的实操证据，不是生产部署证据。

## 48. 你没有真正的 Codebase RAG，为什么 JD 还应该选择你？

> 我已经做了 Codebase RAG 的前置工程：任务检索、规则关联、references、目标仓库事实检查和上下文预算控制；IOC 又提供了真实 RAG、Tool Calling 和 Trace 经验。缺的是把两套能力组合成符号索引、依赖图和混合召回。我能明确说明演进路径，也不会把关键词搜索包装成 RAG。

## 49. 如何证明 AI Coding 的收益不是“自我感觉良好”？

- 建立接入前基线；
- 对相似复杂度任务分层；
- 记录首次生成可用率；
- 记录人工修改时长；
- 统计 Review 问题密度；
- 统计缺陷逃逸率；
- 扣除 Prompt、规则和资产维护成本；
- 样本不足只报告趋势。

## 50. 如果模型升级后原来的 Prompt 失效怎么办？

- 固定评估数据集；
- Prompt、模型和参数版本绑定；
- 离线回归；
- 对失败类型分层；
- 灰度发布；
- 新旧模型并行对比；
- 自动停止和快速回滚；
- 不能假设更强模型天然兼容旧 Prompt。
