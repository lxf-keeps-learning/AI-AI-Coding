# 第一组：项目总述与岗位匹配

## 1. 请用一分钟介绍两个项目，并说明为什么匹配这个岗位。★★★★★

大白话：我有两个项目，一个叫 AI-AI-Coding，一个叫 IOC，正好一个管"生成"，一个管"运行"。

先说 AI-AI-Coding。它解决的是：让 AI 写代码时别瞎写，能照着团队规矩来，写出真正能进工程交付的代码。做法是把 Prompt、Cursor Rules、能跑的 ai-kit、Codegen 技能、检索器、安装器和验证命令串成一条开发期工作流。

再说 IOC。它解决的是：让 Agent 在真实业务里靠谱地跑，不是只会聊天。它用 LangGraph 编排多步分析，通过 Tool Center 调用 KPI、告警、隐患、工单这些工具，还接了报告追问、RAG、Prompt 版本管理和 LangSmith 追踪。

为什么匹配这个岗位？岗位要的三块我都能对上：SDD、流水线、Harness 对应 AI-AI-Coding；Agent、工具调用、RAG、可观测对应 IOC；游戏 A/B 批量生成我还没在生产里做过，但能给迁移方案。

最后主动讲清边界：本地工程闭环有证据，真实效率收益和游戏场景效果要等试点验证。

🗣 一句话记忆版：一个管生成稳定，一个管运行靠谱，两边互补。

## 2. 你在两个项目中的个人职责是什么？

大白话：我先把两边各自干了什么讲清楚。

AI-AI-Coding 里我做了：需求拆解、规则体系、Prompt 模板、ai-kit、检索关联、安装器、验证链路，还有 cascade-filter 这个 SDD 示例。

IOC 里我做了：LangGraph 业务链路、Tool Center、Prompt 治理、Trace/LangSmith、报告追问、可靠性设计。

但一定要分清楚三层：哪些是我自己设计实现的，哪些是项目本来就有的基础，哪些还只是方案。别一上来就说"整个系统全是我一个人从零写的"，那是危险回答，很容易被追问到露馅。可信的说法是："我主导了这几个模块，在已有的基础设施上做了这些改造。"

🗣 一句话记忆版：讲清主导了哪些模块，别吹"全是我从零做的"。

## 3. 两个项目分别解决了什么最核心的问题？

大白话：一句话各说一个。

AI-AI-Coding：把 AI 从"爱怎么写就怎么写"，变成"照着项目事实、团队规则、可信资产来写"。

IOC：把 LLM 从"单轮问答机"，变成"能调业务工具、有证据、可追踪、能降级的业务 Agent"。

一个管"写之前按不按规矩"，一个管"跑起来靠不靠谱"。记住这两个对比就够用了。

🗣 一句话记忆版：一个让 AI 按规矩写，一个让 Agent 靠谱跑。

## 4. 你认为这个 JD 最核心的能力是什么？

大白话：核心不是 Cursor 用得多溜，也不是 Prompt 写得多花哨。真正难的是把模型这种不稳定的东西，包进一套稳定的软件工程系统里。

具体拆成三段：前面用 Spec 把目标定死，别让它瞎猜；中间用上下文和工具把正确率提上去；后面用 Harness、CI/CD 和可观测性把质量守住。

说白了，谁都能让 AI 吐代码，难的是让吐出来的代码能稳定过关、能上线。

🗣 一句话记忆版：把不稳的模型，包进稳定的工程系统。

## 5. 你的最大短板是什么？

大白话：我最大的短板很明确——没做过 Unity/Cocos，也没碰过休闲游戏的 A/B 平台生产环境。

但岗位要的通用底座，比如 TypeScript 工程、SDD、Agent、工具调用、验证和可观测，我都有项目证据。

我的迁移思路是：先挑配置化、低风险的玩法参数和 UI 实验切入，再补 Unity 编译、PlayMode 测试和设备自动化这一层，而不是一上来就动核心玩法引擎。这样风险小，也能快速出东西。

🗣 一句话记忆版：短板是没做游戏，但通用底座都有证据。

# 第二组：AI-AI-Coding 项目深挖

## 6. AI-AI-Coding 不就是一个 Prompt 仓库吗？★★★★★

大白话：看着像，其实不是。它不只有 Markdown 的 Prompt，还装了一大堆别的东西：50 条 Cursor Rules、17 个场景 Prompt、15 个 Vue/TS 的 ai-kit 实现文件、Prompt 和 Rules 和 References 的自动关联、Codegen 技能、业务项目安装器、类型检查、契约检查、Node/Vitest 测试、安全审计，还有个 Prompt Lab。

真正跑起来是一条链：需求 → 检索任务模板 → 加载规则和可信实现 → 检查目标项目事实 → 在业务仓库生成 → 跑验证。

所以它不是一堆文档，是一条能跑通的工作流。

🗣 一句话记忆版：不只是文档，是条能跑通的工作流。

## 7. Rules、Prompt、ai-kit、Skill 分别解决什么问题？★★★★★

大白话：这四样各管一摊，别搞混。

Rules 管长期约束，比如"不许用 any""必须复用已有的请求层"。
Prompt 管这次任务，告诉 AI 这次要干嘛、字段是什么、怎么交互、怎么算验收。
ai-kit 管事实，就是"具体怎么写"的真代码，能照着用。
Skill 管过程，就是多步骤工作流，什么时候触发、按什么顺序做、最后交什么。

还有个优先级要记住：目标项目自己的代码才是最终事实来源，比 AICoding 里的通用示例更权威。

一句话：Rules 管约束，Prompt 管任务，ai-kit 管事实，Skill 管过程。

🗣 一句话记忆版：规则管约束，Prompt 管任务，kit 管事实，Skill 管过程。

## 8. 为什么不写一个超长 System Prompt？

大白话：把所有规则塞进一个超长 System Prompt，看着省事，其实一堆毛病。

上下文噪声变多，AI 容易被无关规则带偏；不相关的规则还可能互相打架；Token 成本蹭蹭涨；想改一条还得翻整篇，不好评审、不好管版本；最关键的是 AI 根本判断不了哪些规则适合当前场景。

所以现在的做法是渐进式披露——只加载最相关的 Prompt、规则和引用文件，用到哪块装哪块。

🗣 一句话记忆版：长 Prompt 又贵又乱，按需加载才靠谱。

## 9. Prompt 如何检索？为什么没有使用向量数据库？

大白话：现在只有 17 个任务 Prompt，用关键词、别名、标题、路径和正文来打分匹配就够了，结果能解释、能离线测。

要是上向量检索，就得额外养 Embedding、索引、服务、版本治理这一整套，成本高还不划算。只有当 Prompt 数量、同义表达、跨领域检索明显超出规则评分的处理能力时，我才会升级成"关键词召回 + 向量召回"的混合检索。

注意：这不是 Codebase RAG，别说自己实现了三层代码索引。

🗣 一句话记忆版：量小用关键词评分，量大了再上向量。

## 10. AI 如何避免虚构接口、字段和依赖？★★★★★

大白话：核心就一条——别让它凭空猜。分几步走：

第一，先读目标项目的 package.json、类型、API 层和相似页面，摸清真实家底；
第二，优先复用目标项目已有的组件；
第三，Prompt 里的示例只当结构参考，不能照抄当事实；
第四，缺关键业务事实时，直接明确提出来问，别硬编；
第五，生成完跑目标项目的 type-check、test、lint、build；
第六，报告没验证过的项，不能用 Mock 通过来冒充真实接入。

🗣 一句话记忆版：先读真代码，缺事实就问，生成完跑验证。

## 11. 为什么 ai-kit 默认不是业务项目的运行时依赖？

大白话：因为各家项目的 Vue、Element Plus、ECharts 和主题版本都不一样，业务项目可能早就有了自己的 BaseComponent。

要是把 ai-kit 硬塞成直接依赖，升级就得跟着耦合，牵一发动全身。所以默认只当开发期参考，目标项目自己的资产优先；只有明确安装或复制了对应资产，才能直接 import。

简单说：先当参考手册用，别急着当依赖挂上。

🗣 一句话记忆版：默认当参考用，装了才能 import。

## 12. 如何防止规则与代码实现发生漂移？

大白话：规则和代码最怕"写着写着就各说各话"。我靠一堆自动检查兜着：

校验 .mdc 的 frontmatter、校验规则引用的路径真的存在、检查 ai-kit 源码里有没有 any、Vue 严格类型检查、Node 和 Vitest 测试、Prompt 静态目录和源文件一致性检查、npm 打包预检确认必要资产真的进了发布包。

后面还想再加强：把这些完整检查接进 CI，建规则测试集，给每条规则加 owner、版本和失败案例来源。

🗣 一句话记忆版：靠自动检查，别让规则和代码两张皮。

## 13. `useRequest` 如何处理请求竞态？

大白话：请求竞态就是"后发的请求先回来，把新数据覆盖了"。

我的做法是：每次请求都递增一个序号，只有最新那个请求才能写进 data、error、loading；旧请求就算后回来，也不能覆盖新结果。

目前这个 cancel 主要是让结果失效，不是真的断开网络；真要中止网络请求，得在 Service 层传 AbortSignal。

追问"为什么不能只用防抖"：防抖只能少发请求，管不住已经发出去的请求谁先回来。

🗣 一句话记忆版：给请求编号，只认最新那个。

## 14. `useDialog` 为什么返回 Promise？

大白话：把弹窗当"确认操作"来对待，调用方就能 await 它的结果，像等一个确认框一样，不用在各个组件之间散落一堆回调。

重复打开时，先用 false 结束上一次的 Promise，避免它悬在那里。loading 状态会锁住关闭入口，防止点太快；异步关闭时拦截的异常，通过事件上报出去。

🗣 一句话记忆版：把弹窗当确认操作，用 await 拿结果。

## 15. `useChart` 最难处理的工程问题是什么？

大白话：图表组件最麻烦的是"时机"和"清理"两件事。

时机上：DOM 还没挂载，option 和 loading 就已经到了；主题切换要重建实例；高频更新得合并；深度监听大型 option 成本很高。

清理上：ResizeObserver 和窗口监听要释放；卸载时必须清干净实例、监听器和定时器，不然内存泄漏。

一句话：时机要准，清理要净。

🗣 一句话记忆版：时机要准，清理要净。

## 16. 你如何证明仓库自身是可执行的？

大白话：我能拿出一串历史验收证据：50 条规则契约检查通过、15 个 Vue/TS 文件严格类型检查通过、9 项 Node 测试、10 项 Vitest、ECharts 6.1.0、当次安全审计 0 漏洞、npm 打包预检包含 107 个文件。

边界要讲清楚：这些证明的是仓库自己的契约能执行，不等于所有业务项目都能零修改接入。

🗣 一句话记忆版：能证明自己可跑，不等于别人零改接入。

## 17. 你怎么理解 SDD？★★★★★

> SDD 不是让你先吭哧吭哧写一大堆没人看的文档。它的核心是：先把"咱们到底要啥、做到什么程度算过关"写成一份机器和人都能照着对照检查的契约（可以理解成一张"验收清单 + 规格说明书"合体）。  
> 后面写设计、拆任务、写代码、跑测试、最后验收，全都指着这同一份契约说话，谁也不能临时改口径。  
> 这么干有两个好处：第一，AI 不用去瞎猜那些没明说的隐含需求，猜错了代价很大；第二，错误尽量在便宜的时候就被揪出来——写文档时发现错，比上线后才发现，成本差了不知道多少倍。

🗣 一句话记忆版：先定契约，后面全照它来。

## 18. 你在项目中如何落地 SDD？★★★★★

> 我走的是这么一条线：  
> 模糊需求 → PRD-SPEC（把目标和验收说清楚）→ HLD（定模块、数据流、接口）→ LLD（把组件 API 和类型写死）→ 写代码和验证 → 按 Spec 验收，再把失败的案例回流回去补 Spec。  
> 可以理解为：先画好图纸，再动工，最后对着图纸验收。  
> 但边界我得说清楚：cascade-filter 已经有 PRD-SPEC、HLD、LLD 和组件实现了，不过 LLD 还标着"评审中"，专属的任务拆分（TASKS）、专项测试、Code Review、上线验收材料都还没补齐。所以它是"SDD 实操案例"，不是"完整生产交付"，这点千万别吹过头。

🗣 一句话记忆版：图纸先行，案例已做、交付未完。

---

### 📌 概念补充：PRD / HLD / LLD / TASKS 四层文档怎么区分（记不住就看这里）

**先破缩写**：HLD = High-Level Design = 高层/概要设计（粗）；LLD = Low-Level Design = 低层/详细设计（细）。高=看得远但模糊，低=看得近但清楚。

**盖房子类比**：

| 文档 | 回答的问题 | 类比 | cascade-filter 里长这样 |
|------|-----------|------|------------------------|
| PRD-SPEC | 要做什么？做到啥样算好？ | 业主要求：三室一厅朝南 | 需求背景 + 验收标准 |
| HLD | 大框架怎么搭？ | 建筑总图：户型/承重墙/水电走线 | 用级联组件、三个接口、状态放组件内、4 个 ADR |
| LLD | 每个零件具体啥样？ | 施工图：每面墙尺寸、插座精确位置 | CascadeFilter.vue 的 props、useCascadeOptions 方法、类型定义 |
| TASKS | 先干哪步后干哪步？ | 施工计划：先砌墙再刷漆 | 任务清单 + 依赖顺序 |

**一句话记法**：PRD 说"要什么"，HLD 说"怎么搭"，LLD 说"搭成什么样"，TASKS 说"先干哪个"。颗粒度越来越细。

**面试答法**（背这句）：
> "HLD 是概要设计，定模块、接口、数据流这些大框架；LLD 是详细设计，把组件 API、类型、函数都写死，能直接照着写代码。PRD 定需求，HLD 定架构，LLD 定代码细节。"

## 19. Spec 至少应该包含哪六类信息？★★★★★

> 一份合格的 Spec，至少要把这六件事写清楚：  
> 1. 背景、用户和目标——这活儿是给谁干、为了啥；  
> 2. 功能行为和优先级——先做啥、后做啥、哪些必须做；  
> 3. 输入、输出和接口契约——进去什么、出来什么，长什么样；  
> 4. 状态、异常和边界条件——出岔子了怎么办；  
> 5. 非功能要求和约束——性能、安全这些硬指标；  
> 6. 可验证的验收标准和观测指标——怎么算"做完了、做对了"。  
> 一句话：这六类写全了，AI 才不用靠猜，验收也才有依据。

🗣 一句话记忆版：目标、行为、接口、异常、约束、验收。

## 20. cascade-filter 最初需求是什么？你做了哪些澄清？

> 最初就一句模糊的话：做个三级筛选框。光这一句根本没法动手，所以我把它澄清成了这些点：  
> 它是个通用组件，不能绑死省市区或组织结构；数据要一级一级懒加载，别一口气全拉回来；UI 用 Cascader；"不限"要能动态配置；要支持已有值回显；上级变了必须清空下级；加载失败要显示错误、允许重试；只选到二级也算有效的筛选范围。  
> 这就好比别人只说"做道菜"，你得先问清楚：几个人吃、忌口、辣的还是不辣的，才能动锅。

🗣 一句话记忆版：一句话需求，先拆成八条细节。

## 21. cascade-filter 的关键架构决策是什么？

> 我做了四个 ADR（就是四个关键的岔路口决定）：  
> 1. 用 Cascader 一个组件，而不是三个独立下拉；  
> 2. 用懒加载，而不是一开始全量加载；  
> 3. 把 `fetchOptions` 通过函数注入进来，而不是在组件里写死 URL；  
> 4. 用 `allowEmpty` 配置化，而不是把业务行为焊死。  
> 追问"为什么用函数注入"：是为了把鉴权、URL、数据格式这些差异隔离在外面，让组件只依赖一个稳定的领域契约，谁用都行、互不污染。

🗣 一句话记忆版：四个决定，选一不选三、注入不写死。

## 22. cascade-filter 如何处理回显？

> 回显就是打开组件时，把已经选好的值原样填回去。我的做法是：  
> 先设一个 `hydrating` 状态，回显期间禁止用户操作，免得半途改乱了；然后按一级到三级的顺序加载；每级都校验目标 ID 到底存不存在；某级值失效了，就截断到上一级为止；回显会同步 `modelValue`，但不触发用户主动的 `change`（因为这不是用户干的）；懒加载和预热同时发生时，用 in-flight Promise 去重，避免重复请求。  
> 可以理解成：表单回填时先锁住，一格一格对，对不上就退回去，还不惊动别人。

🗣 一句话记忆版：回显先锁、逐级对、失效就截断。

## 23. cascade-filter 当前设计里有什么潜在问题？★★★★★

> 我主动认这些坑：  
> - `CascadeLevel` 写死成 `1 | 2 | 3`，但 Props 又声称支持 2/3/4 级，类型和实际能力对不上；  
> - 缓存主要用 level 当键，同一级切换不同 parent 时，可能返回错父节点的数据，更合理的键应该是 `level + parentId`；  
> - LLD 里写了组件测试，但当前目录还没看到对应的专项测试；  
> - 加载失败现在主要是弹消息提示，面板里到底有没有"重试按钮"，还得继续补；  
> - PRD 要求清空下级，但组件现在依赖 Cascader 内部值变化，缓存清理是不是真的完整触发了，还得验证。  
> 讲这些不是自曝其短，是说明我会主动审视自己代码的边界。

🗣 一句话记忆版：类型冲突、缓存键错、测试待补。

## 24. 你是否实现了 Spec DSL？

> 没有。我目前做的是结构化 Markdown 模板和文档约定，还不是那种有解析器、能做 Schema 校验、能编译出东西的正式 DSL。所以我会叫它"Spec Schema 或模板体系"，不叫 DSL。  
> 下一步可以把核心字段抽成 YAML/JSON Schema，做静态校验，再自动生成任务、测试骨架和发布元数据。  
> 划重点：千万别说"我已经设计并上线了 Spec DSL"，那是吹牛，我现在只有模板。

🗣 一句话记忆版：只有模板约定，不是正式 DSL。

## 25. 什么是 Harness Engineering？★★★★★

> Harness 就是套在模型生成过程外面的一圈"确定性的工程设施"。模型这东西是飘的，会瞎编，所以要用一圈靠谱的装置把它框住。  
> 这圈装置包括：上下文准备、工具权限控制、执行沙箱、编译测试、质量评分、失败恢复、发布门禁。  
> 打个比方：模型是流水线上的工人，负责提出"候选实现"；Harness 就是质检流水线，负责证明这份候选到底能不能进下一道工序。  
> 一句话：模型负责"猜"，Harness 负责"证"。

🗣 一句话记忆版：模型提候选，Harness 来证明。

---

## 26. 你会如何设计六层 AI Coding Harness？★★★★★

> 我把它分成六层，像六道关卡：  
> L1 Spec Harness——校验目标、接口、边界、验收条件齐不齐；  
> L2 Context Harness——检索相关规则、代码、依赖、相似实现，检查引用有没有效；  
> L3 Generation Harness——限制文件范围、工具权限、依赖和变更预算；  
> L4 Static Harness——格式、lint、类型、依赖、安全扫描；  
> L5 Runtime Harness——单测、组件测试、集成、构建、游戏运行测试；  
> L6 Delivery Harness——Diff Review、风险评分、人工审批、灰度、回滚、线上观测。  
> 对应到我的项目：AI-AI-Coding 已经较好覆盖 L1、L2、L4 和部分 L5；L3 有 Skill/Rules 的流程约束，但沙箱和权限还得加强；L6 的 CI、真实试点、灰度、线上指标还没闭环。

🗣 一句话记忆版：六层关卡，L6 还没闭环。

---

## 27. 请设计一条"Spec 进、部署出"的流水线。★★★★★

> 就是一条流水线：需求进去，能部署的东西出来。大致是：  
> 需求输入 → Spec 完整性检查 → HLD/LLD 与风险分级 → 任务依赖图 → 建隔离分支或工作区 → 检索 Codebase Context → AI 生成代码 → 静态检查 → 单元/集成/构建/游戏测试 → 自动 Review 与风险评分 → 人工批准 → 灰度部署 → 指标观察 → 自动停止或回滚。  
> 关键设计点有六条：  
> - 幂等：每个任务有唯一 Spec ID；  
> - 可恢复：每阶段产物存下来，能从失败那一步重试；  
> - 隔离：每个变体独立分支、独立构建产物；  
> - 可追踪：Spec、Prompt、模型、提交、构建都能对上号；  
> - 门禁：高风险变更不许自动部署；  
> - 回滚：留着上一版稳定构建和配置。  
> 就像工厂流水线，每一道都留痕、能停、能退。

🗣 一句话记忆版：进 Spec 出部署，全程留痕可回滚。

---

## 28. 如何把"天级变小时级"变成可验证目标？

> 光喊"效率翻倍"没用，得先定好"量什么"。我按阶段采这些指标：  
> - 需求到 Spec 定版：澄清轮数、等待时长；  
> - Spec 到首个候选代码：模型执行时长；  
> - 首次生成到检查通过：人工修改时长、重试次数；  
> - 检查通过到可 Review：构建与测试时长；  
> - Review 到实验包：人工等待和部署时长。  
> 核心指标就是：Lead Time（交付周期）、首次通过率、人工干预率、重试次数、各阶段失败分布，还有 P50/P90 交付时长。  
> 有了这些数，"天级变小时级"才从口号变成能核对的数字，否则就是自我感觉良好。

🗣 一句话记忆版：先定指标，再谈提速。

---

## 29. 如何提高首次通过率？

> 思路是一层层扒失败在哪，再对症下药：  
> 1. 先分析失败发生在哪一层；  
> 2. 补齐 Spec 的输入输出和边界；  
> 3. 改进检索，让模型拿到正确的相似代码；  
> 4. 把高频失败固化成规则；  
> 5. 把失败案例加进回归数据集；  
> 6. 减少单次任务的变更范围；  
> 7. 对不同任务选不同模型或 Prompt。  
> 最后一条红线：不能靠"减少测试"来抬高通过率，那是作弊，等于把质检删了假装良品率高。  
> 本质是：让模型一次就拿到对的上下文、做对的事。

🗣 一句话记忆版：扒失败层、补 Spec、别删测试。

---

## 30. 如何降低人工干预率？

> 核心是让"本来不用人管的事"自动解决，人只出现在真正需要拍板的地方：  
> - 把反复出现的澄清项直接写进 Spec 模板；  
> - 把反复出现的 Review 问题变成静态规则；  
> - 让错误输出结构化、自动分类；  
> - 低风险失败允许自动修复、有限次重试；  
> - 超过重试预算、或碰到高风险目录，才升级给人。  
> 但要注意：我们要的是"有效干预"的减少，不是为了把数字做漂亮就取消必要的审批。该人工把关的（比如高风险变更），照样得留人。

🗣 一句话记忆版：能自动的自动，该把关的留人。

# 题库大白话改写 · Part 3（题 31-40）

> 本文件是把原题库第 31-40 题的答案"翻译"成大白话，方便面试前背诵。  
> 口径不变：只讲代码和验收能证明的事，不夸大。

## 31. IOC 的 Agent 主链路是什么？★★★★★

你可以把它想成一条流水线：用户带着页面上下文进来，先走 LangGraph 做运营分析，需要数据就去 Tool Center 查 KPI、告警、隐患、工单。查完用规则识别问题，再让 LLM 分析原因，最后汇总成建议和报告。用户如果继续追问，就走追问节点；追问需要依据时再调 RAG 查制度、标准。整个过程每一步都留 Trace、留事件、留结果，方便回头查。技术栈就是 Vue 3 前端、FastAPI 后端，走 REST 加 SSE 实时推，数据存 MySQL，模型用 DeepSeek 这类 OpenAI 兼容接口。

🗣 一句话记忆版：页面进、查数据、分析、报告、追问、RAG、全留痕。

## 32. 为什么使用 LangGraph，而不是普通链式调用？

普通链式调用就像一根绳子从头串到尾，中间哪步错了很难回头。LangGraph 像个流程图：节点和状态边界很清楚，能走条件分支，某步失败了可以降级或恢复，Tool、RAG、LLM 各管各的、分开看。中间查到的证据可以塞进 State，就像任务进度本，后面随时用。想加报告追问、多个 Agent、人工确认节点也方便。但我要补一句：如果整条链路永远只是一次 Prompt、一次模型调用，那我不会为了用框架硬上 LangGraph，杀鸡不用牛刀。

🗣 一句话记忆版：节点清晰、能分支能降级、State 存证据。

## 33. Tool Center 解决了什么问题？★★★★★

Tool Center 像公司的统一服务台。以前每个工具各写各的，接口五花八门，现在统一注册和发现，统一输入输出契约，统一错误语义还带 `retryable`（能不能重试）。Trace、耗时、Evidence 也统一记。Graph、API 和其他 Agent 都共用这一个工具层，不用重复造。工具再分成 Query（查询）、Analysis（分析）、Action（动作）三层，Action 类工具支持人工确认，避免乱动手。

🗣 一句话记忆版：统一注册、统一契约、统一留痕、Action 要人批。

## 34. 工具调用如何避免越权或误操作？

思路是"能不给的权限就不给"。先把工具分查询、分析、动作三级，用白名单圈定能用哪些，每个工具的参数 Schema 写死。用户和页面上下文一路透传下去。动作类工具默认只生成草稿，不直接执行，还要带 `requires_human_confirmation` 人工确认。加超时、重试、审计，敏感输入先脱敏。生产环境再叠 RBAC 权限和网关授权。一句话：先分级、再白名单、动作要人批、全程留审计。

🗣 一句话记忆版：分级白名单、动作要人批、敏感脱敏。

## 35. IOC 的 RAG 与 Codebase RAG 有什么区别？★★★★★

两者查的东西完全不一样。IOC 的 RAG 是查制度、标准、案例，给业务回答当依据，属于"业务知识库"。Codebase RAG 是查代码的符号、依赖、调用链和历史变更，给代码生成当上下文，属于"代码知识库"。要特别说清楚：AI-AI-Coding 现在只是关键词检索，不是完整的 Codebase RAG，别把关键词搜索包装成 RAG。

🗣 一句话记忆版：IOC 查业务依据，Codebase RAG 查代码上下文。

## 36. 如果设计 Codebase RAG，你会如何做三层索引？

我会分三层建索引。第一层文件层：目录、语言、模块、README、配置。第二层符号层：类、函数、组件、Hook、类型、API 和 import 图。第三层语义和历史层：代码块的向量、提交记录、Review 结论、失败案例。检索时先用关键词/BM25 召回，再靠符号和依赖图扩展，加向量召回，然后做权限过滤、重排，最后按 Token 预算组装上下文。这里要强调：这是基于现有经验的演进设计，还没实现，不能包装成已经做完了。

🗣 一句话记忆版：文件、符号、语义三层，召回扩展再重排。

## 37. IOC 如何做可观测性？★★★★★

可观测性就是让每个环节都"能查到"。本地用 `trace_id` 把请求、日志、工具、数据库审计串起来。LangGraph 记录每个节点的开始、完成、失败和耗时。LangSmith Trace 则画出 Graph、Node、LLM、Tool、RAG 的父子执行树，像族谱一样看谁调用了谁。另外 Prompt 治理还会记 `prompt_key`、`prompt_version`、`prompt_commit_hash`、`environment`，这样出了问题能一路追回去。

🗣 一句话记忆版：trace_id 串全链路，节点事件加执行树。

## 38. LangSmith 在项目中真实做到了什么？

要诚实说边界。代码层确实做完了：Graph、Node、LLM、Tool、RAG 都接了 Trace，做了脱敏、采样和本地 traceId 关联。Prompt 发布前的 private Commit 同步、失败保护和 Commit 复用，是用 Fake Client 做的自动化验收。但这轮没用真实账号上传业务 Prompt 和 Trace，所以远程端到端还没验证，得在隔离环境里再验。

🗣 一句话记忆版：Fake Client 验收完，远程端到端没验。

## 39. Prompt 管理中心为什么不是普通 CRUD？

普通 CRUD 就是随便增删改查，管理中心不一样。它把 Prompt 分成 System、Business、Runtime Context、User Question 几层。版本不可变，有草稿、审核、发布、回滚的状态流转。production 只读 active release，绝不读最新草稿。还带测试、评估、实验、失败案例。Graph 节点会记下用的是哪个版本，发布前同步 LangSmith Commit。就算管理中心挂了，也能回退到本地 Prompt，不会整个停摆。

🗣 一句话记忆版：分版本不可变、生产只读已发布、挂了能回退。

## 40. IOC 中最值得讲的排障案例是什么？

建议讲"后端成功但前端失败"这个案例。现象是：创建版本的接口返回 200，看起来成功；但紧接着的预览接口返回 422。根因是前后端对字段契约理解不一致——项目里本来就有 PreviewRequest，结果路由却复用了 RenderRequest。最后统一成 `version_id`，并补了 API 回归测试。这个故事的价值在于：说明你会顺着整条请求链查问题，而不是看到数据库写入成功就收工。

🗣 一句话记忆版：200 后 422，字段契约不一致，回归测试补上。

# 第六组：游戏 A/B 实验场景题

## 41. 一个玩法如何一天生成 5–10 个变体？

先别一上来就想"变魔术式地改代码"，先想一件事：**哪些东西值得变，哪些东西不能乱动**。所以第一步是把玩法拆成两部分——一部分是"地基"（基础玩法 Spec），这是所有变体共用的；另一部分是"旋钮"（可变参数），比如方块生成概率、难度曲线、奖励频率、UI 反馈强度、引导节奏、关卡目标这些。

第二步，把这堆旋钮整理成一个"变体矩阵"，像做菜的不同配方一样：换一勺盐、多放点辣，就出来一个不同的菜。每个配方对应一份 Variant Spec，每份都有自己的唯一 ID。

第三步才是动代码：每个变体建一个隔离分支，AI 只在受限文件里改，别让它顺手把公共逻辑也改了。改完 Harness 自动跑验证，生成独立构建，再接入实验配置。

关键要守住三条：**能配置就不写死**、**变体之间互斥**、**实验指标和停止规则在生成前就定好**——别等跑起来了才发现不知道怎么收场。

🗣 一句话记忆版：旋钮+矩阵，隔离生成，实验先定规则。

## 42. 如何避免十个变体变成十条维护分支？

先说最省事的做法：**能改配置的，绝不复制代码**。十个变体如果只是参数不一样，那它们不该是十个分支，而是一个代码 + 十套配置。用 Feature Flag 或者 Remote Config 去开关，稳定逻辑大家共用一份，只有真正的"机制差异"才值得生成代码。

再说生命周期：变体不是养一辈子。过期的及时归档，实验跑完，获胜的那个合并进主路径，其他的一律删掉——别让它们像堆在角落的旧衣服一样越积越多。

最后补一条保险：**配置 Schema 和代码版本要绑死**。否则你改了代码，老配置还对不上，分支没省下来，反而多了一堆"薛定谔的 bug"。总结一句：配置化优先，共用为主，过期就清，赢了合并，输了删除。

🗣 一句话记忆版：能配置就别开分支，赢了合并输了删。

## 43. 变体生成后如何自动验证？

验证的思路是"从便宜到贵、一层层往上筛"，别一上来就上真机。先做最便宜的：Spec 和配置 Schema 对不对，然后编译（C#/TS），能编译过再跑单元测试。

再往上是 Unity 专属的 EditMode / PlayMode 测试，看看游戏跑起来到底行不行。接着查资源和场景引用有没有断，比如引用的 Prefab 丢没丢。

然后上"可复现的试玩"：用固定随机种子做模拟运行，保证每次跑的结果能对比。再盯性能、内存、包体积这些阈值，别让一个变体把包塞爆了。

最后是"眼见为实"：关键页面截图或视频对比，确认埋点埋全了，再留一道人工试玩门禁。记住顺序——**编译 → 测试 → 引用 → 模拟 → 性能 → 画面 → 人工**，一道不过就别往后走。

🗣 一句话记忆版：从便宜到贵层层筛，最后留人工门禁。

## 44. 如何判断 A/B 实验结果可信？

A/B 实验本质上是**对照试验**，像做科学实验一样，结论不是"看着好看"就行。先要在实验前就把主指标和护栏指标定死——不能跑完了再看哪个数字好看就选哪个。

然后是分桶：用户要随机分流，而且得稳定，别今天在 A 明天在 B。样本量要提前估够，别跑了两天就下结论；中途反复偷看数据再提前喊停，是最容易翻车的坑。

还要分层看：新用户、国家、设备这些维度都得检查，别让"某个地区突然暴增"污染了整体结论。看指标要看一组，留存、时长、付费、崩溃、性能一起看，不能只盯一个付费。

最后两条容易被忽略：变体多的时候要做**多重比较校正**，否则一堆变体里总有一个"看起来显著"其实是碰运气；而且"统计显著"不等于"业务上值得做"，提升 0.1% 可能根本不值得上线。

🗣 一句话记忆版：先定指标再分桶，别偷看、别只看一个数。

## 45. 如果没有 Unity 经验，如何做 Unity Prompt 优化？

先主动承认边界，但别停在"我不会"。我的思路是：**不把 Vue 那套 Prompt 直接照搬过去**，因为 Unity 的世界完全不一样。

第一步是先摸清 Unity 的真实约束——程序集、场景、Prefab、MonoBehaviour 生命周期、序列化字段、资源加载方式、测试命令，这些就是"事实来源"。先了解环境，再谈优化。

第二步才是建 Unity 专属的 Rules 和 Few-shot。比如：禁止在 Update 里分配内存（会卡）、资源要及时释放、注意主线程限制这些 Unity 特有的坑，都要写进规则里。

第三步用数据说话：拿编译、EditMode、PlayMode 和真机性能数据来评估 Prompt 改得好不好，而不是凭感觉。总结顺序：**先摸环境 → 再定专属规则 → 最后用真机数据验证**。

🗣 一句话记忆版：先摸 Unity 约束，再定规则，用真机验证。

# 第七组：压力追问与边界防守

## 46. 你说端到端流水线，为什么项目里还没有 CI？

这个问题考的是"你敢不敢承认缺口"。我的态度是：**不狡辩，先说清现状，再说下一步**。

现状是：我跑通的是**本地可执行流水线和文档门控**，这是真的；但 CI 确实没接，这是个明确的缺口。所以我从来不会把它吹成"生产级无人交付平台"，那是不诚实的。

下一步的路线也很清楚：先把 `npm run check`、安全审计、打包预检、最小业务示例这些先接进 CI，把地基打牢；再逐步加隔离分支、构建产物和部署门禁。顺序就是：**先承认 → 再定边界 → 最后给路线图**。面试官要的不是完美，是看你敢不敢直面问题、有没有清晰的补法。

🗣 一句话记忆版：先认缺口，再给一步步补法。

## 47. cascade-filter 为什么还不能证明"Spec 进、部署出"？

先划清楚"已经证明了什么"和"还没证明什么"。cascade-filter **已经证明了**从需求澄清到设计再到实现的这条链路——也就是 SDD 的"生产前"部分，这是真实存在的证据。

但"部署侧"证据确实不足：专项测试、Code Review、上线 Checklist、真实业务接入这些都还没补齐。所以它的定位要说得准确：它是 **SDD 的实操证据**，不是**生产部署证据**。

别把这两件事混在一起。面试官问这个，就是想看你有没有清醒的自我认知——会不会把"设计出来了"当成"上线了"。顺序就是：**先肯定已证明的 → 再指出缺失的 → 最后给个准确结论**。

🗣 一句话记忆版：证明的是链路，不是上线。

## 48. 你没有真正的 Codebase RAG，为什么 JD 还应该选择你？

先别慌，这个问题的关键是"你已经把前置工程做完了"。我确实没有完整的 Codebase RAG，但我做了它前面的**所有准备工作**：任务检索、规则关联、references、目标仓库事实检查、上下文预算控制——这些就是 Codebase RAG 的地基。

而且 IOC 项目给了我**真实的 RAG、Tool Calling 和 Trace 经验**，这是另一块拼图。我缺的只是把这两套能力拼起来——做成符号索引、依赖图和混合召回。

关键加分点是：我能**清楚说出演进路径**，并且我**从来不会把关键词搜索包装成 RAG**。一个诚实、知道下一步怎么走的人，比一个吹嘘自己啥都做了的人更值得选。顺序：**先认差距 → 再亮前置积累 → 最后给路径和诚实态度**。

🗣 一句话记忆版：前置工程已做完，路径清楚不吹牛。

## 49. 如何证明 AI Coding 的收益不是"自我感觉良好"？

核心就一句：**用数字说话，别用感觉说话**。怎么拿数字？先建立**接入前的基线**——不然你说"效率提升了"，提升的起点在哪儿都没定。

然后把任务按难度分层，相似难度的放一起比，别拿"简单任务"和"复杂任务"混着算。要记的指标有一串：首次生成可用率、人工修改时长、Review 问题密度、缺陷逃逸率。

还有一条特别容易被漏掉：**要扣除成本**。Prompt、规则、资产维护这些都要算进去，否则"省了开发时间"但"多了维护时间"，账是算不平的。

最后是诚实：如果样本太少，就只说"趋势"，别硬说"结论"。顺序：**先定基线 → 再分层统计 → 再扣成本 → 样本不够只报趋势**。

🗣 一句话记忆版：先定基线再算账，样本少只报趋势。

## 50. 如果模型升级后原来的 Prompt 失效怎么办？

先接受一个事实：**更强的模型不一定天然兼容旧 Prompt**，这是常态，不是意外。所以不能假设"升级了自然更好"。

应对的招数是一套"保险机制"，先说最重要的：**固定评估数据集**。有一套标准题，模型一升级就跑一遍，能不能用、哪里退化了，一眼就能看出来。

然后是**版本绑定**：Prompt、模型、参数要绑在一起记录，出问题才能定位是谁的锅。再配合离线回归、按失败类型分层，搞清楚是"理解错了"还是"格式变了"。

上线要**灰度**，新旧模型并行对比，别一刀切。再留一手**自动停止和快速回滚**，一旦指标变差马上退回去。顺序：**先认事实 → 固定评估集 → 版本绑定回归 → 灰度+回滚兜底**。

🗣 一句话记忆版：固定评估集，灰度上线，随时能回滚。
