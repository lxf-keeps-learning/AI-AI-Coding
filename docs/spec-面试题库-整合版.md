## 7. Rules、Prompt、ai-kit、Skill 分别解决什么问题？★★★★★

### 📄 原答案（技术说明）

- **Rules**：长期约束，例如禁止 `any`、必须复用已有请求层。
- **Prompt**：本次任务的目标、字段、交互和验收条件。
- **ai-kit**：真实可执行参考，回答“具体怎么写”。
- **Skill**：多步骤工作流，规定什么时候触发、按什么顺序执行、交付什么。
- **目标项目代码**：最终事实来源，优先级高于 AICoding 的通用示例。

一句话：

> Rules 管约束，Prompt 管任务，ai-kit 管事实，Skill 管过程。


### 🗣 大白话解析

大白话：这四样各管一摊，别搞混。

Rules 管长期约束，比如"不许用 any""必须复用已有的请求层"。
Prompt 管这次任务，告诉 AI 这次要干嘛、字段是什么、怎么交互、怎么算验收。
ai-kit 管事实，就是"具体怎么写"的真代码，能照着用。
Skill 管过程，就是多步骤工作流，什么时候触发、按什么顺序做、最后交什么。

还有个优先级要记住：目标项目自己的代码才是最终事实来源，比 AICoding 里的通用示例更权威。

一句话：Rules 管约束，Prompt 管任务，ai-kit 管事实，Skill 管过程。

🗣 一句话记忆版：规则管约束，Prompt 管任务，kit 管事实，Skill 管过程。

## 8. 为什么不写一个超长 System Prompt？

### 📄 原答案（技术说明）

- 上下文噪声增加；
- 无关规则可能冲突；
- Token 成本增加；
- 修改难以评审和版本化；
- AI 难以判断哪些规则适用于当前场景。

当前方案是渐进式披露，只加载最相关 Prompt、规则和引用文件。


### 🗣 大白话解析

大白话：把所有规则塞进一个超长 System Prompt，看着省事，其实一堆毛病。

上下文噪声变多，AI 容易被无关规则带偏；不相关的规则还可能互相打架；Token 成本蹭蹭涨；想改一条还得翻整篇，不好评审、不好管版本；最关键的是 AI 根本判断不了哪些规则适合当前场景。

所以现在的做法是渐进式披露——只加载最相关的 Prompt、规则和引用文件，用到哪块装哪块。

🗣 一句话记忆版：长 Prompt 又贵又乱，按需加载才靠谱。

## 13. `useRequest` 如何处理请求竞态？

### 📄 原答案（技术说明）

- 每次请求递增序号；
- 只有最新请求可以写入 `data/error/loading`；
- 旧请求即使后返回，也不能覆盖新结果；
- 当前 cancel 主要是结果失效；
- 真正网络中止应在 Service 层传递 `AbortSignal`。

**追问：为什么不能只用防抖？**  
防抖只能减少请求，不能保证所有已发请求的返回顺序。


### 🗣 大白话解析

大白话：请求竞态就是"后发的请求先回来，把新数据覆盖了"。

我的做法是：每次请求都递增一个序号，只有最新那个请求才能写进 data、error、loading；旧请求就算后回来，也不能覆盖新结果。

目前这个 cancel 主要是让结果失效，不是真的断开网络；真要中止网络请求，得在 Service 层传 AbortSignal。

追问"为什么不能只用防抖"：防抖只能少发请求，管不住已经发出去的请求谁先回来。

🗣 一句话记忆版：给请求编号，只认最新那个。

## 14. `useDialog` 为什么返回 Promise？

### 📄 原答案（技术说明）

- 调用方能像等待确认操作一样接收结果；
- 避免多组件间散落回调；
- 重复打开时先用 `false` 结束上一次 Promise，避免悬空；
- loading 状态锁定关闭入口；
- 异步关闭拦截异常通过事件上报。


### 🗣 大白话解析

大白话：把弹窗当"确认操作"来对待，调用方就能 await 它的结果，像等一个确认框一样，不用在各个组件之间散落一堆回调。

重复打开时，先用 false 结束上一次的 Promise，避免它悬在那里。loading 状态会锁住关闭入口，防止点太快；异步关闭时拦截的异常，通过事件上报出去。

🗣 一句话记忆版：把弹窗当确认操作，用 await 拿结果。

## 15. `useChart` 最难处理的工程问题是什么？

### 📄 原答案（技术说明）

- DOM 挂载前 option/loading 已经到达；
- 主题切换需要重建实例；
- ResizeObserver 和窗口监听需要释放；
- 高频更新需要合并；
- 深度监听大型 option 成本高；
- 卸载时必须清理实例、监听器和定时器。


### 🗣 大白话解析

大白话：图表组件最麻烦的是"时机"和"清理"两件事。

时机上：DOM 还没挂载，option 和 loading 就已经到了；主题切换要重建实例；高频更新得合并；深度监听大型 option 成本很高。

清理上：ResizeObserver 和窗口监听要释放；卸载时必须清干净实例、监听器和定时器，不然内存泄漏。

## 17. 你怎么理解 SDD？★★★★★

### 📄 原答案（技术说明）

> SDD 不是先写很多文档，而是先把需求转成机器和人都能检查的契约，再让设计、任务、代码、测试和验收都引用同一份契约。它的价值是减少 AI 在隐含需求上的猜测，并把错误尽量前移到低成本阶段发现。


### 🗣 大白话解析

> SDD 不是让你先吭哧吭哧写一大堆没人看的文档。它的核心是：先把"咱们到底要啥、做到什么程度算过关"写成一份机器和人都能照着对照检查的契约（可以理解成一张"验收清单 + 规格说明书"合体）。  
> 后面写设计、拆任务、写代码、跑测试、最后验收，全都指着这同一份契约说话，谁也不能临时改口径。  
> 这么干有两个好处：第一，AI 不用去瞎猜那些没明说的隐含需求，猜错了代价很大；第二，错误尽量在便宜的时候就被揪出来——写文档时发现错，比上线后才发现，成本差了不知道多少倍。

🗣 一句话记忆版：先定契约，后面全照它来。

### 📌 概念补充：PRD / HLD / LLD / TASKS 四层文档怎么区分（记不住就看这里）

**先破缩写**：HLD = High-Level Design = 高层/概要设计（粗）；LLD = Low-Level Design = 低层/详细设计（细）。高=看得远但模糊，低=看得近但清楚。

**盖房子类比**：

| 文档 | 回答的问题 | 类比 | cascade-filter 里长这样 |
|------|-----------|------|------------------------|
| PRD-SPEC | 要做什么？做到啥样算好？ | 业主要求：三室一厅朝南 | 需求背景 + 验收标准 |
| HLD | 大框架怎么搭？ | 建筑总图：户型/承重墙/水电走线 | 用级联组件、三个接口、状态放组件内、4 个 ADR |
| LLD | 每个零件具体啥样？ | 施工图：每面墙尺寸、插座精确位置 | CascadeFilter.vue 的 props、useCascadeOptions 方法、类型定义 |
| TASKS | 先干哪步后干哪步？ | 施工计划：先砌墙再刷漆 | 任务清单 + 依赖顺序 |

**一句话记法**：PRD 说"要什么"，HLD 说"怎么搭"，LLD 说"搭成什么样"，TASKS 说"先干哪个"。颗粒度越来越细。

**面试答法**（背这句）：
> "HLD 是概要设计，定模块、接口、数据流这些大框架；LLD 是详细设计，把组件 API、类型、函数都写死，能直接照着写代码。PRD 定需求，HLD 定架构，LLD 定代码细节。"

## 21. cascade-filter 的关键架构决策是什么？

### 📄 原答案（技术说明）

四个 ADR：

1. Cascader，而不是三个独立下拉；
2. 懒加载，而不是全量加载；
3. 注入 `fetchOptions`，而不是组件写死 URL；
4. `allowEmpty` 配置化，而不是写死业务行为。

**追问：为什么使用函数注入？**  
隔离鉴权、URL 和数据格式差异，使组件只依赖稳定领域契约。


### 🗣 大白话解析

> 我做了四个 ADR（就是四个关键的岔路口决定）：  
> 1. 用 Cascader 一个组件，而不是三个独立下拉；  
> 2. 用懒加载，而不是一开始全量加载；  
> 3. 把 `fetchOptions` 通过函数注入进来，而不是在组件里写死 URL；  
> 4. 用 `allowEmpty` 配置化，而不是把业务行为焊死。  
> 追问"为什么用函数注入"：是为了把鉴权、URL、数据格式这些差异隔离在外面，让组件只依赖一个稳定的领域契约，谁用都行、互不污染。

## 22. cascade-filter 如何处理回显？

### 📄 原答案（技术说明）

- 设置 `hydrating`，回显过程中禁止操作；
- 一级到三级顺序加载；
- 每级校验目标 ID 是否存在；
- 某级值失效时截断到上一级；
- 回显同步 `modelValue`，但不触发用户主动的 `change`；
- 懒加载与预热并发时通过 in-flight Promise 去重。


### 🗣 大白话解析

> 回显就是打开组件时，把已经选好的值原样填回去。我的做法是：  
> 先设一个 `hydrating` 状态，回显期间禁止用户操作，免得半途改乱了；然后按一级到三级的顺序加载；每级都校验目标 ID 到底存不存在；某级值失效了，就截断到上一级为止；回显会同步 `modelValue`，但不触发用户主动的 `change`（因为这不是用户干的）；懒加载和预热同时发生时，用 in-flight Promise 去重，避免重复请求。  
> 可以理解成：表单回填时先锁住，一格一格对，对不上就退回去，还不惊动别人。

🗣 一句话记忆版：回显先锁、逐级对、失效就截断。

## 41. 一个玩法如何一天生成 5–10 个变体？★★★★★

### 📄 原答案（技术说明）

```text
基础玩法 Spec
+ 可变参数 Schema
+ 约束条件
+ 变体矩阵
→ 生成 5–10 份 Variant Spec
→ 每份创建隔离分支
→ AI 修改受限文件
→ Harness 自动验证
→ 生成独立构建
→ 接入实验配置
```

可参数化内容：方块生成概率、难度曲线、奖励频率、UI 反馈强度、引导节奏和关卡目标。

关键约束：配置优先；保证变体互斥；每个变体有唯一 ID；实验指标和停止规则在生成前定义。


### 🗣 大白话解析

先别一上来就想"变魔术式地改代码"，先想一件事：**哪些东西值得变，哪些东西不能乱动**。所以第一步是把玩法拆成两部分——一部分是"地基"（基础玩法 Spec），这是所有变体共用的；另一部分是"旋钮"（可变参数），比如方块生成概率、难度曲线、奖励频率、UI 反馈强度、引导节奏、关卡目标这些。

第二步，把这堆旋钮整理成一个"变体矩阵"，像做菜的不同配方一样：换一勺盐、多放点辣，就出来一个不同的菜。每个配方对应一份 Variant Spec，每份都有自己的唯一 ID。

第三步才是动代码：每个变体建一个隔离分支，AI 只在受限文件里改，别让它顺手把公共逻辑也改了。改完 Harness 自动跑验证，生成独立构建，再接入实验配置。

关键要守住三条：**能配置就不写死**、**变体之间互斥**、**实验指标和停止规则在生成前就定好**——别等跑起来了才发现不知道怎么收场。

🗣 一句话记忆版：旋钮+矩阵，隔离生成，实验先定规则。

## 42. 如何避免十个变体变成十条维护分支？

### 📄 原答案（技术说明）

- 优先参数化和配置化；
- 使用 Feature Flag/Remote Config；
- 稳定逻辑共用；
- 只有机制差异才生成代码；
- 变体过期后及时归档；
- 获胜变体合并为主路径，其他变体删除；
- 配置 Schema 和代码版本绑定。


### 🗣 大白话解析

先说最省事的做法：**能改配置的，绝不复制代码**。十个变体如果只是参数不一样，那它们不该是十个分支，而是一个代码 + 十套配置。用 Feature Flag 或者 Remote Config 去开关，稳定逻辑大家共用一份，只有真正的"机制差异"才值得生成代码。

再说生命周期：变体不是养一辈子。过期的及时归档，实验跑完，获胜的那个合并进主路径，其他的一律删掉——别让它们像堆在角落的旧衣服一样越积越多。

最后补一条保险：**配置 Schema 和代码版本要绑死**。否则你改了代码，老配置还对不上，分支没省下来，反而多了一堆"薛定谔的 bug"。总结一句：配置化优先，共用为主，过期就清，赢了合并，输了删除。

🗣 一句话记忆版：能配置就别开分支，赢了合并输了删。

## 43. 变体生成后如何自动验证？

### 📄 原答案（技术说明）

2. C#/TS 编译；
3. 单元测试；
4. Unity EditMode/PlayMode 测试；
5. 资源和场景引用检查；
6. 固定随机种子的模拟运行；

### 🗣 大白话解析

最后是"眼见为实"：关键页面截图或视频对比，确认埋点埋全了，再留一道人工试玩门禁。记住顺序——**编译 → 测试 → 引用 → 模拟 → 性能 → 画面 → 人工**，一道不过就别往后走。

🗣 一句话记忆版：从便宜到贵层层筛，最后留人工门禁。

## 44. 如何判断 A/B 实验结果可信？

### 📄 原答案（技术说明）

- 实验前明确主指标和护栏指标；
- 随机分流且用户稳定分桶；
- 样本量估算；
- 避免中途反复偷看并提前下结论；
- 检查新用户、国家、设备等分层；
- 同时看留存、时长、付费、崩溃和性能；
- 多变体时控制多重比较；
- 结果显著不代表业务价值一定足够大。


### 🗣 大白话解析

A/B 实验本质上是**对照试验**，像做科学实验一样，结论不是"看着好看"就行。先要在实验前就把主指标和护栏指标定死——不能跑完了再看哪个数字好看就选哪个。

然后是分桶：用户要随机分流，而且得稳定，别今天在 A 明天在 B。样本量要提前估够，别跑了两天就下结论；中途反复偷看数据再提前喊停，是最容易翻车的坑。

还要分层看：新用户、国家、设备这些维度都得检查，别让"某个地区突然暴增"污染了整体结论。看指标要看一组，留存、时长、付费、崩溃、性能一起看，不能只盯一个付费。

最后两条容易被忽略：变体多的时候要做**多重比较校正**，否则一堆变体里总有一个"看起来显著"其实是碰运气；而且"统计显著"不等于"业务上值得做"，提升 0.1% 可能根本不值得上线。

🗣 一句话记忆版：先定指标再分桶，别偷看、别只看一个数。
