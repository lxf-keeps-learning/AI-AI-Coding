# PRD-SPEC Enhancer（PRD 完善专家）

将一段 MRD 或原始 PRD，转化为一份**可指导研发直接开发**的 PRD-SPEC（Markdown）。
核心机制：**逐项检查 → 自动补全 → 自检 → 交互式收集缺口 → 渲染输出**。

## 适用与不适用

- 适用：输入是 MRD / 原始 PRD / 需求片段，需要检查完整性、补全缺口、产出规范 PRD-SPEC。
- 不适用：非需求类文本；纯代码审查；已完整无需补全的成稿（可仅做检查）。

## 资产结构

| 文件 | 作用 | 何时读取 |
|------|------|----------|
| [spec/checklist.md](spec/checklist.md) | 元素检查清单：必要性 + 触发条件 + 补全动作 | Step2/Step3 逐项判定 |
| [spec/prd-spec-template.md](spec/prd-spec-template.md) | 产出物骨架模板（固定小节） | Step6 渲染输出 |
| [spec/lexicon.md](spec/lexicon.md) | 业务词典（探测式激活，默认休眠） | Step3 命中业务指向时 |

## 知识来源（按优先级）

1. **输入提取**：从用户传入内容中直接获取。
2. **自身推理**：基于上下文与常识合理推断（推断项需在产出中标注 `≈推断`）。
3. **AICoding 已有资产**（补全时参考，不照抄）：
   - `design/_templates/`：PRD/HLD/LLD/TASKS 模板基线
   - `.cursor/rules/`：组件/页面/性能规范（决定"可开发"的具体形态）
   - `src/ai-kit/`：已有组件与 Hook（决定"必须复用"）
   - `design/<slug>/`：同 slug 已产出的上游文档
4. **交互确认**：仍缺的真实业务信息（字段枚举、接口、权限）→ 标 `⚠️待确认`，Step5 一次性集中提问。

## 执行流程（必须严格按顺序）

复制以下清单并跟踪进度：

```
- [ ] Step1 解析输入：判定类型(MRD/PRD)、抽取已有信息、识别成熟度
- [ ] Step2 加载 checklist.md：对每个元素跑触发条件，判定必要性(必备/条件必备/可选)
- [ ] Step3 补全：输入提取 → 自身推理 → 检索 AICoding 资产 → 标记风险项
- [ ] Step4 自检：是否仍有【必备】或【已命中的条件必备】缺口
- [ ] Step5 若有缺口 → 一次性集中发起交互式确认 → 回填
- [ ] Step6 按 prd-spec-template.md 渲染输出 Markdown
```

### Step1 解析输入
- 判断输入是 MRD（偏市场/为什么做）还是 PRD（偏怎么做），据此决定补全重心。
- 抽取已有信息，记录"已提供 / 部分提供 / 缺失"三态，供后续对照。

### Step2 判定必要性
- 读取 [spec/checklist.md](spec/checklist.md)，对每个元素执行其"触发条件"。
- 必要性三级：**必备**（恒定必须）、**条件必备**（命中触发条件才必须）、**可选**（复杂需求才需要）。
- PRD 不是制式文件：未命中触发条件的元素不强求，避免过度膨胀。

### Step3 补全
按"知识来源"优先级为每个"需要但缺失"的元素取数。
- 推断项标 `≈推断`；AICoding 资产引用的可标 `(ai-kit)` / `(rules)`。
- 取不到的真实业务信息 → 标 `⚠️待确认`，**不编造**。

### Step4 自检
- 仅对**必备**与**已命中的条件必备**元素校验是否已填充有效内容。
- 可选元素、未命中条件的元素不计入缺口。

### Step5 交互式确认（仅在自检存在缺口时）
- **一次性集中提问**：把所有缺口整理成一个清单，一次性向用户询问，不要边补边频繁打断。
- 用户回填后再次执行 Step3→Step4，直到无必备缺口。

### Step6 渲染输出
- 严格套用 [spec/prd-spec-template.md](spec/prd-spec-template.md) 的固定小节。
- **完整骨架**：所有板块均列出；不适用的小节保留标题并标注"本需求不涉及"，而非删除。
- 来源标注（精简）：**默认不标即为已确认**；仅显式标注两类风险项——`≈推断`（AI 补全，需研发复核）、`⚠️待确认`（未定，需补齐并汇总到文末）。

## 降级策略

- 资产检索无返回或与需求无关时：该项标 `⚠️待确认`，纳入 Step5 交互清单，**不得编造业务数据**。
- 推断内容必须显式标注 `≈推断`，便于研发复核；已确认/原始输入内容不标注。

## 关键原则

- 不臆造真实业务名词、字段枚举、接口——拿不到就标 `⚠️待确认`。
- 输出面向研发：可开发、可测试、边界清晰优先于辞藻完整。
- 术语一致：全程统一使用"元素 / 板块 / 触发条件 / 必要性"等词汇。
- **复用优先**：凡是 ai-kit 已有能力（搜索/表单/树/级联/useRequest 等），在补全"方案类"内容时必须标注应复用，禁止默认重复造轮子。
