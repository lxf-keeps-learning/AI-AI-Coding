# 抽取判定标准

## 核心心法

> 过早抽象比重复更可怕。

本项目的 ai-kit 沉淀只接受**经过真实业务验证**的能力。"看起来通用"不是抽取理由,"实际被 ≥ 2 个业务正确使用"才是。

## 四象限判定

对每段疑似可抽的代码,沿两个维度打分:

- **重复度**:在当前业务代码里出现几次?
- **稳定度**:API 形态、参数语义是否清晰收敛?会不会在下一个业务里需要大改?

| 重复度 | 稳定度 | 结论 |
|--------|--------|------|
| ≥ 2 处 | 稳定(用法一致、参数语义清晰) | **建议抽取**:写进改造清单 |
| ≥ 2 处 | 不稳定(参数发散、形态差异大) | **暂不抽取**:在报告里建议先用"约定 + 代码片段"统一,等再出现 1-2 次稳定后再抽 |
| 1 处 | 看起来稳定 | **观察项**:不写进改造清单,记录到"观察项"section |
| 1 处 | 不稳定 | **保持现状**,不进报告 |

## 抽取必须满足的硬条件

候选项进入"建议新抽取"清单之前,逐条核对:

1. **覆盖 ai-kit 已有边界之外** — 不是和 BaseDialog/useTable 等已有能力重叠
2. **能写出非 `any` 的 TypeScript 契约** — 写不出来说明语义还不稳定
3. **能写出符合项目模板的 AI 注释** — 如果连"什么时候用、什么时候不用"都难描述,说明边界还没收敛
4. **存放路径明确** — `src/ai-kit/<category>/` 中应当归到哪个 category
5. **配套 .cursor/rule 能写得出** — 至少能写 5-10 行有抓手的规则

任意一条不满足 → 退回观察项,不抽。

## 抽取的最小信息单元

每个进入清单的项,在报告里必须包含:

```
名称: BaseXxx.vue / useXxx.ts
路径: src/ai-kit/<category>/
覆盖场景: <1-2 句话>
当前在业务里出现的位置:
  - src/views/a/foo.vue:120-180
  - src/views/b/bar.vue:60-110
契约草稿:
  - Props: ...
  - Emits: ...
  - Returns: ...
AI 注释草稿: <按 annotation-template.md 写>
配套规则:
  - 新建 .cursor/rules/<category>/xxx.mdc
  - 在 .cursor/rules/global/base.mdc 的"公共能力目录"表追加一行
验收标准:
  - 业务方 A、B 替换后回归通过
  - 旧实现完全移除
工作量估计: <0.5/1/2 人日>
```

字段不全的不进清单。

## 反模式自检

写改造清单前自查,有任一命中就退回观察项:

- [ ] 我只看到了 1 处真实用例,但凭"直觉"觉得"以后肯定会用"
- [ ] 候选契约里出现了 `any` 或 `Record<string, any>` 占位
- [ ] 候选名称需要超过 3 个修饰词才能解释清(`BaseSmartAutoFillSearchFormWithPaging`)
- [ ] 候选 API 在两处用例之间需要 ≥ 3 个差异化 prop 来抹平
- [ ] 业务方调用时还需要复制大段 slot 模板 — 说明抽得太浅
- [ ] 抽完之后,ai-kit 现有的某个组件功能与之大量重叠(应优先扩展现有组件)

## 复用 vs. 抽取 vs. 留在原地的标语

- **复用**:ai-kit 里已有,业务方却没用 → 这是事故,P0 改回
- **抽取**:ai-kit 没有,但 ≥ 2 处真实业务在重复造 → 这是机会,排进改造清单
- **留在原地**:只 1 处,或耦合业务太深 → 这是常态,克制冲动
