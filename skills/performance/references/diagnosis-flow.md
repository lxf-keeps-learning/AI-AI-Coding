# 性能诊断流程

> 没有症状,就没有诊断。这份文件是症状采集 + 路由到瓶颈的总入口。

## 症状采集清单

把这些问题问到位再开始推方案。如果用户只给了代码,自己从代码里"演化"出这些答案,并在报告里注明"症状由代码推断"。

### A. 现象描述

- [ ] 哪个页面 / 路由?
- [ ] 哪个交互动作触发?(进入页 / 滚动 / 切 tab / 提交 / 输入 / hover)
- [ ] 现象是什么?(白屏 / 掉帧 / 长时间无响应 / 浏览器假死)

### B. 复现条件

- [ ] 是首次出现还是用一段时间后出现?(用一段时间后才慢 → 高度怀疑内存)
- [ ] 数据量级?(行数 / 节点数 / 数据点数)
- [ ] 仅在某浏览器/低配机出现还是普遍?
- [ ] 开发还是生产?

### C. 度量证据

- [ ] Performance 火焰图 / Lighthouse / Web Vitals 数据
- [ ] 内存截图(Memory tab,堆快照前后对比)
- [ ] 网络瀑布图(资源大小、TTFB、并发数)
- [ ] FPS 实测(滚动场景特别需要)
- [ ] 控制台错误 / 警告 / Vue warn

### D. 关键代码线索

- [ ] 涉及的组件/Hook 路径
- [ ] 列表/表格/图表的数据来源
- [ ] watch / computed / effect 的依赖
- [ ] 全局事件订阅、定时器、第三方实例(echarts / map / video)

## 症状 → 瓶颈映射表

| 症状关键字 | 首选怀疑 | 次要怀疑 | 路由到 |
|------------|----------|----------|--------|
| "进入页面就卡 / 白屏 N 秒" | 网络(首屏资源大、TTFB 长)| 网络瀑布 + 主线程长任务 | network.md → render.md |
| "滚动掉帧 / 滚一会就慢" | 渲染(行数过多、无 key、子组件无 memo) | 大数据 / 列虚拟化 | render.md → large-data.md |
| "列表加载完就卡死" | 大数据(一次性渲染过多 DOM) | 渲染 + 计算 | large-data.md → render.md |
| "图表初始化卡" | 图表(数据点过多、动画过重) | 大数据 | chart.md → large-data.md |
| "图表 resize 卡 / tooltip 卡" | 图表(未节流、未 dispose) | 渲染 | chart.md → render.md |
| "切 tab 才慢" | 图表/表格隐藏时未延迟初始化 | 资源加载 | chart.md → render.md |
| "用一会儿越来越慢" | 内存(监听/定时器/实例未清理) | 计算(深 watch 累积) | memory.md → compute.md |
| "Tab 一直开着内存涨" | 内存 | 大对象 reactive | memory.md |
| "搜索/输入卡顿" | 计算(无防抖、深 watch) | 网络(每次输入打请求) | compute.md → network.md |
| "提交后好久才响应" | 网络(等服务端) | 计算(大对象 reactive 跟踪开销) | network.md → compute.md |
| "首页 LCP 不达标" | 网络(关键资源体积/瀑布) | 渲染(首屏组件过重) | network.md → render.md |

## 数据量级阈值参考(用来回答"是不是大数据")

| 场景 | 关注阈值(超过即需要专门优化) |
|------|--------------------------------|
| 表格行数 | > 100 行,前端全量分页是反模式;> 200 行考虑虚拟滚动 |
| 表格列数 | > 15 列,需要列稳定引用 + 必要时使用 useMemo |
| 折线图数据点 | > 1000 点,启用 sampling;> 10000 点必须降采样或聚合 |
| 树节点 | > 500 节点,启用懒加载 |
| 一次返回的列表数据 | > 1MB JSON,考虑分页 / 增量;> 5MB 必须改 |
| watch 监听对象 | 不允许 `deep: true` + 大对象 reactive 组合 |

这些阈值不是绝对标准,但越过就要在报告里**显式说明并触发对应 reference**。

## 度量基线工具

报告必须给出"改造前 baseline + 改造后目标"。常用度量工具:

| 维度 | 工具 / 指标 |
|------|--------------|
| 加载 | Lighthouse(LCP / TTI / TBT / CLS) |
| 运行时帧率 | Performance 面板的 frames,或 `performance.now()` 手动埋点 |
| 内存 | Memory tab → 堆快照,关注 Detached DOM / Retained size |
| 长任务 | Performance 面板长任务标签(> 50ms) |
| 网络 | Network 瀑布图、Coverage 面板 |
| Vue 渲染 | Vue Devtools 的组件渲染统计 |

如果用户没条件采,**告诉他们要采**,把"采集 baseline" 作为 P0 改造项写进报告。

## 不要做的事

- 在症状还没问清楚时就推方案
- 把"看着应该慢"当成"实际很慢"的依据
- 把所有问题归到"数据太多" — 那是最常见的错诊
- 引入 `shallowRef` / `markRaw` / `v-memo` / 虚拟滚动等"重武器"前,先确认它们解决的是已观测到的问题,而不是想象中的问题
